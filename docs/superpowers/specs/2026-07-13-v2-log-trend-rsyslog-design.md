# V2 日志趋势、维护页和 RSyslog 接收设计

## 背景

当前 V2 测试版已部署到 `192.168.0.142:8080`。已知问题集中在三块：

1. 仪表盘“日志趋势”应按天展示，并能区分设备 ID。
2. 维护页需要改成纵向结构，避免右侧卡片撑高和操作区拥挤。
3. 日志源存在中文乱码，同时 V2 需要加入 RSyslog 接收能力。

142 服务器 root 密码已改为 `Qjkj@86902290`。RSyslog 接收器默认端口为 `5514`，但必须支持自定义端口。

## 目标

- 趋势图按日期显示，不再使用小时刻度。
- 趋势数据支持设备维度，能看全部设备和单个设备。
- 维护页面使用纵向布局：扫描计划、入库操作、版本升级依次排列。
- 修复项目内已知中文乱码默认文案，不把乱码写入新设置。
- 新增 RSyslog 接收源，先做到“接收落盘，再复用现有导入流程入库”。

## 非目标

- 第一版不做复杂多设备堆叠图。
- 第一版不直接把 syslog 消息写入 ClickHouse。
- 第一版不引入外部 rsyslog 进程配置管理；由 fwlog 自身提供轻量接收器。
- 第一版不做公网暴露安全策略，只提供本机服务配置和端口监听能力。

## 设计一：日志趋势图按天和设备展示

### 后端数据契约

当前 `log_trend` 是 `DistributionItem[]`，只有 `name/value`。需要扩展为结构化趋势点：

```json
{
  "log_trend": [
    {
      "date": "2026-07-13",
      "source_id": "default",
      "log_tag": "深信服 NAT",
      "value": 12345
    }
  ]
}
```

保留字段含义：

- `date`：日志日期，格式 `YYYY-MM-DD`。
- `source_id`：设备 ID。
- `log_tag`：设备展示名称。
- `value`：该设备该日期的日志行数。

查询按最近 14 天返回，包含有数据的设备维度。前端负责补齐“全部设备”的日期序列和单设备日期序列中的空洞。

### 前端展示

- X 轴显示日期，例如 `07-01`、`07-02`。
- 默认展示“全部设备”聚合量。
- 图表头部增加设备选择：
  - `全部设备`
  - 每个 `source_id / log_tag`
- 没有日志时显示空状态和 0 基线，不显示重复的 `1、1、1` 刻度。

## 设计二：维护页方案 C

维护页不再使用左右拼接大卡片。改为纵向结构：

1. 扫描计划
   - 自动扫描开关
   - 扫描时间
2. 入库操作
   - Source 选择
   - 手动入库按钮
   - 重建日期
   - 重建按钮
   - 全量重建开关
3. 版本升级
   - 当前版本
   - 更新状态
   - 检查更新
   - 离线升级包上传

每块都是独立卡片，宽度跟随页面内容区。移动端仍然自然纵向排列。

### 维护页统一文案

维护页所有用户可见文案必须和项目现有中文风格统一，避免中英文混用，避免“自动升级”这种容易误解为后台自动执行的表达。

页面主标题保持：

- 上方说明：`配置和维护`
- 标题：`系统设置`

Tab 文案保持：

- `日志源`
- `IP 库`
- `维护`
- `登录`

维护页卡片和字段文案统一为：

| 扫描计划标题 | `扫描计划` |
| 扫描计划小标签 | `自动扫描` |
| 自动扫描状态 | `已开启` / `已关闭` |
| 扫描时间 | `扫描时间` |
| 入库卡片标题 | `入库操作` |

## 设计三：中文乱码修复

已确认 `web/src/api.ts` 的 mock/demo 数据中存在 `娣变俊鏈?NAT` 这类乱码。后端默认配置 `internal/config/config.go` 中的默认值是正常的 `深信服 NAT`。

修复范围：

- 替换前端 mock/demo 中的乱码中文。
- 检查 Go 源码、打包脚本、测试文案中的已知乱码；只改会进入页面、接口、日志或安装输出的用户可见文案。
- 后端设置加载时增加窄范围兼容：如果旧设置值等于已知乱码默认值，则显示和保存为 `深信服 NAT`。

不做泛化编码猜测，避免误改用户自定义设备名。

## 设计四：RSyslog 接收器

### 日志源模型

日志源增加类型：

```json
{
  "source_id": "fw-a",
  "log_tag": "防火墙 A",
  "enabled": true,
  "source_type": "file",
  "log_dir": "/data/sangfor_fw_log"
}
```

RSyslog 接收源：

```json
{
  "source_id": "fw-a",
  "log_tag": "防火墙 A",
  "enabled": true,
  "source_type": "rsyslog",
  "listen_protocol": "udp",
  "listen_host": "0.0.0.0",
  "listen_port": 5514,
  "spool_dir": "/data/fwlog/received/fw-a"
}
```

默认值：

- `source_type`: `file`
- `listen_protocol`: `udp`
- `listen_host`: `0.0.0.0`
- `listen_port`: `5514`
- `spool_dir`: `/data/fwlog/received/<source_id>`

### 接收流程

1. fwlog 启动时读取启用的 RSyslog 源。
2. 为每个启用源启动 UDP 监听器。
3. 收到消息后按当前日期追加到：

```text
/data/fwlog/received/<source_id>/YYYY-MM-DD.log
```

4. 自动扫描或手动入库继续走现有 importer，从该目录读取日志文件。

### 端口冲突和错误处理

- 如果端口被占用，该源接收器进入错误状态，但不阻断 fwlog 主服务启动。
- 页面显示该源接收状态：运行中、已停用、端口占用、启动失败。
- 保存设置后重启接收器配置，不要求重启整个 fwlog 服务。

### 第一版协议范围

第一版先实现 UDP。配置模型保留 `listen_protocol`，后续可扩展 TCP。页面上协议可以先固定展示 UDP，避免承诺未实现能力。

## 验证计划

- 后端单测：
  - 趋势 SQL 按 `log_date, source_id, log_tag` 聚合。
  - 日志趋势响应包含设备维度。
  - RSyslog UDP 接收器能把消息落盘到 source spool 目录。
  - 端口冲突不阻断 App 启动。
- 前端测试：
  - 趋势图使用日期标签和设备筛选。
  - 0 数据不生成重复 Y 轴刻度。
  - 维护页 CSS 不再使用左右跨行布局。
  - 日志源表单根据 source type 展示文件目录或 RSyslog 端口。
- 集成验证：
  - `npm test`
  - `npm run build`
  - `go test ./...`
  - 在 142 上升级测试包后，用 UDP 5514 发送一条 syslog，确认落盘并可触发入库。

## 风险和回滚

- RSyslog 接收器会新增监听端口，需要确认服务器防火墙允许需要的 UDP 端口。
- 接收落盘目录会持续增长，后续需要补充清理策略；第一版先不自动删除原始接收文件。
- 如果 RSyslog 接收器异常，可禁用该日志源或改回 `source_type=file`，现有文件导入流程不受影响。
