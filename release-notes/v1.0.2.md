# v1.0.2 修复记录草稿

## 目标

`v1.0.2` 聚焦银河麒麟现场部署后的稳定性和可观测性，不做架构级变更。主要处理 244 服务器巡检发现的问题，并在数据概览页补充 CPU、内存、数据库状态小组件，让运维人员可以第一眼判断服务是否健康。

## 本次补充

- 数据概览页新增系统资源状态：
  - CPU 负载
  - 内存使用率
  - ClickHouse 数据库状态
- `/api/health-dashboard` 新增 `system_health` 字段，前端不再靠静态文案推测状态。
- 数据库状态展示 ClickHouse 版本、活跃查询、后台 merge、active parts 等核心指标。
- 修复系统设置页扫描时间始终保存为 `01:00` 的问题。
- 优化自动扫描关闭时的页面文案：设置页标明“启用后生效”，入库进度页显示“自动扫描未启用 / 手动入库”，不再把禁用态误写成“下次扫描未启用”。
- 入库接近完成时，进度文案从长期显示 `99%` 调整为 `收尾中`，降低误判为卡死的概率。

## 待修复问题

### 银河麒麟 RPM 安装后服务可能先于 ClickHouse 就绪启动

部署环境：

- 服务器：`192.168.244.244`
- 系统：银河麒麟 V10 x86_64
- 安装包：`nat-query-service_kylin-server_amd64.rpm`
- 版本：`nat-query-service-1.0.1-1.x86_64`

现象：

- RPM 安装过程会同时启动 `fwlog-clickhouse.service` 和 `nat-query-service.service`。
- `nat-query-service` 首次启动时，ClickHouse 9000 端口尚未就绪。
- 服务出现两次启动失败记录，随后 systemd 自动重启后恢复正常。

失败日志：

```text
2026-07-06 10:19:12 nat-query-service panic: open clickhouse: dial tcp 127.0.0.1:9000: connect: connection refused
2026-07-06 10:19:22 nat-query-service panic: open clickhouse: dial tcp 127.0.0.1:9000: connect: connection refused
```

当前状态：

- `fwlog-clickhouse.service`：`active/running`
- `nat-query-service.service`：`active/running`
- `http://192.168.244.244:8080/api/session`：`200`
- `http://192.168.244.244:8080/`：`200`

修复方向：

- `nat-query-service.service` 增加启动前 ClickHouse ready 检查。
- 或后端启动连接 ClickHouse 时增加有限重试，避免安装阶段直接 panic。
- RPM/DEB 安装脚本应先等待 ClickHouse ready，再启动 `nat-query-service`。

### 历史日期导入中时，进度接口可能显示 idle

部署后巡检时间：`2026-07-06 10:30 CST`

现象：

- ClickHouse 中存在正在导入的日期：
  - `source_id=外网`
  - `log_date=2026-05-13`
  - `status=importing`
  - `files_done=19`
  - `files_total=42`
  - `progress_pct=45.23809523809524`
- 同时 `/api/ingest-progress` 返回：

```json
{
  "status": "idle",
  "dates": []
}
```

影响：

- 页面可能显示“空闲”，但后台实际仍在写入 ClickHouse。
- 运维人员无法判断安装后是否正在自动导入，也无法看到历史日期回填进度。

修复方向：

- 进度接口应优先返回当前 `status=importing` 的日期，不应只受默认时间窗口影响。
- 进度页需要明确区分“无任务”和“正在导入历史日期”。

### RPM 首次安装后默认自动扫描会立即开始导入

现象：

- `app_settings.auto_scan_enabled=true`
- 安装后服务启动，后台开始扫描 `/data/sangfor_fw_log` 并导入历史归档。
- 服务器日志目录当前文件数约 `6207`。
- 巡检期间 ClickHouse 有活跃 `INSERT INTO nat_logs`。

影响：

- 首次安装后会直接消耗 CPU、磁盘 IO 和 ClickHouse 写入资源。
- 如果用户只是想先验证安装或调整配置，会被自动导入打断。

修复方向：

- 新安装默认关闭自动扫描，或首次进入页面由用户确认后开启。
- 保留升级场景的既有设置，不覆盖用户已经保存的配置。

### ClickHouse 数据目录放在根分区下

现状：

- ClickHouse 数据目录：`/opt/nat-query/clickhouse/data`
- 所在分区：`/`
- 根分区容量：`44G`
- 根分区当前使用率：`65%`
- `/data` 分区容量：`492G`，当前使用率：`2%`

影响：

- NAT 日志持续导入后，ClickHouse 数据会优先撑满根分区。
- 根分区满会影响系统和服务稳定性。

修复方向：

- 默认 ClickHouse 数据目录迁移到 `/data/nat-query/clickhouse/data`。
- RPM/DEB 安装包需要处理新装目录和升级兼容。

### RPM 升级后旧 DuckDB 文件残留

残留文件：

- `/opt/nat-query/libduckdb.so`，约 `50M`
- `/data/index/nat_logs.duckdb`，约 `2.6G`
- `/data/index/nat_logs.duckdb.wal`，约 `1.1M`
- `/data/index/nat_logs.duckdb.tmp/`

影响：

- 占用空间。
- `/data/index` 同时放 GeoIP 和旧数据库文件，目录职责混乱。
- 运维人员容易误判当前服务仍依赖 DuckDB。

修复方向：

- 升级脚本不要自动删除旧数据，但应输出明确提示。
- 提供单独的清理/迁移脚本，由用户确认后执行。

### ClickHouse 运行环境有 THP 警告

日志：

```text
Linux transparent hugepages are set to "always".
```

影响：

- ClickHouse 官方通常建议关闭 Transparent Huge Pages，避免查询和写入时出现抖动。

修复方向：

- 安装包或自检脚本检测 THP 状态。
- 文档提示将 THP 设置为 `never` 或 `madvise`。

### 服务器存在无关失败单元

巡检发现：

```text
lm_sensors.service loaded failed failed Hardware Monitoring Sensors
```

影响：

- 与 fwlog 服务无直接关系。
- 但 `systemctl --failed` 会显示失败项，容易干扰部署验收。

处理建议：

- 记录为服务器环境问题，不放入 fwlog 安装包修复范围。
